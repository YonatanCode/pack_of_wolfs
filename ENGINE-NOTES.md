## 2. Hypothetical orders (P2 requirement)

`dryRunTurn()` previews **only the player orders currently queued**; passing `options.queues` is refused. The unvalidated override exists only as `dryRunTurnInternal` for fixtures. Before any hypothetical-order entry point is exposed to the Battle Lab, **P2 must validate such orders against the same hand, card consumption and action budgets as real play** (`activeRules.playerActionBudget`, hand contents, first-match removal). **L1 status (section 10):** `validatePlayerOrders` is that validation, shared with the UI click paths; `applyPlayerOrders` / `runHeadlessTurn` apply validated orders to the LIVE battle. `dryRunTurn` is unchanged (still only the queued orders); a validated hypothetical preview on a copy is not part of L1.

## 3. Partial-turn error behaviour (existing; follow-up)

`executePlayerActionQueue` runs the turn end in a `finally`. If the rules core throws mid-turn, the already-applied part of the turn is **kept (no rollback)**, and recovery, hand refill, the next-turn preview, idle animations and the outcome check still run. This matches the behaviour before X2; the fixtures pin it. **Deferred follow-up:** atomic live execution. No automatic dry run before Play is added. Committing from a copy conflicts with the step-by-step replay, so a different design is needed.

## 4. Testing boundary

Permitted: bounded, hand-authored regression fixtures (`node tests/run-all.cjs`, at most 3 turns each, scripted terminal outcomes allowed).
Not permitted without explicit approval: randomized comparisons, bots, full synthetic battles, tuning sweeps. Synthetic testing needs the user's manual playcheck of the exact candidate build, then a separate explicit authorization of its bounded manifest.

**Record of the reviewer's 40 randomized comparisons (P1e review):**
- The independent reviewer (Sonnet 5.5) wrote a throwaway script, `fuzz.cjs`, in the session scratch directory. It is not in the repo and was not saved. The coordinator did not ask for randomized runs; the reviewer chose to run them, and the coordinator included the result in a report without flagging that it went beyond the hand-authored boundary.
- **Scope:** headless Node harness with a virtual clock, no browser, no LLM calls. A fixed pseudo-random generator (seed 12345) built 40 boards from the intro scenario: random positions, facing and health (1-7) for up to six units (some optional units absent), 0-5 random hill tiles and 0-2 random trees, and every fourth board (10 of 40) in stag mode. Player wolves got 0-2 random actions each, with a fallback of one Attack for the lead wolf.
- **Per board:** one `dryRunTurn`, then one real turn through `executePlayerActionQueue`, comparing events and final state. If no player orders remained and both sides were alive, a second turn with fixed scripted orders (lead Move, support Attack) was compared the same way.
- **Turn limits:** at most 2 turns per board (80 maximum). No board was played to a natural end. No bot or strategy chose orders.
- **Result as reported by the reviewer:** 0 mismatches. It is not reproducible from the repo, it is not part of the regression suite, and no gate relies on it. It must not be rerun without the user's approval.

## 6. Per-battle settings (P2a)

Presets `current` (the default) and, since the follow-up step, the limited experimental `commander` preset (section 8). **Changing any setting intentionally changes gameplay and balance; the UI notice says so.** Default settings are byte-identical to before (the whole existing fixture suite is the regression for them).

**Settings and bounds (`SETTINGS_BOUNDS`).** All values must be finite integers (no coercion: `"5"`, `"5abc"`, `1.5`, `NaN`, `Infinity`, `null`, `undefined`, booleans are rejected). The player budget is shared by the whole pack; the enemy budget is independent.

| Key (panel / state) | Link | Default | Bounds |
|---|---|---|---|
| `playerActionBudget` | `pab` | 5 | 1..8 |
| `handSize` | `hs` | 5 | 1..8 |
| `reshuffleCharges` | `rc` | 2 | 0..9 |
| `maxSameAction` | `cap` | 3 | 1..8 |
| `weightMove` / `weightAttack` / `weightDefend` | `wm` / `wa` / `wd` | 1 / 1 / 1 | 0..20 each |
| `enemyActionBudget` | `eab` | 5 | 0..10 (0 = the enemy passes, supported) |
| `poolMove` / `poolDefend` / `poolAttack` | `epm` / `epd` / `epa` | 2 / 1 / 2 | 0..10 each |

The enemy pool is stored as counts and expanded to `RULES.perBattle.enemyActionPool` in the canonical order Move, Defend, Attack (defaults give exactly `[Move, Move, Defend, Attack, Attack]`). `RULES` itself is unchanged.

**Cross-field rules** (all problems are reported together, never just the first). Errors block Apply: at least one weight > 0 ("at least one draw weight must be greater than 0"); the hand must be fillable: (actions with weight > 0) x `maxSameAction` >= `handSize`. Warnings are shown but allowed: `playerActionBudget` > `handSize` ("at most N cards can be queued per turn; the budget is not resized"); `enemyActionBudget` > pool size ("the enemy can plan at most N actions (pool size); neither budget nor pool is resized"); budget > 0 with an empty pool ("the enemy has nothing to plan"). Nothing is ever silently resized. The usable enemy budget is min(budget, pool size); the planner may use fewer (recording unassigned actions is P2b).

**Pending vs active.** The panel edits `pending`; `activeSettings` (frozen) drives `takeActiveRulesSnapshot()`. Active changes only through `applyPendingSettings()` = refuse while busy (throws `DryRunRejected`: turn executing, swap active, tutorial, world mode; nothing changes) -> validate pending (invalid: refused, nothing changes) -> set active -> `restartBattle()` (terrain, units, hand size, budget, charges, pool and RNG reset together). The Restart button, the R key and Play Again restart with the ACTIVE settings; pending is not applied by them. "Reset pending" sets pending to the defaults without applying (since section 14: the default battle setup).

**Record and hash.** `activeRules.hash` is recomputed with `computeRulesHash` from the full effective rules (RULES with `perBattle` replaced); default settings give `0d3ce2ec6fa6de`. `devTest.getEffectiveRulesRecord()` returns `{ preset, customized, version, hash, settings, values }`. `getRulesRecord`, `getBattleSeeds` and `getBattleRecord` are unchanged.

**Link.** `?scenario=<id>&seed=<n>&preset=current&rules=<k>:<v>,<k>:<v>`: only non-default keys, in the key order of the table; default settings emit no `rules` (and, before section 14, no `preset`; now `preset=current`, because a link without preset / rules boots the default battle setup). Parsing is strict: an unknown or duplicate key, a malformed pair, a non-integer or out-of-bounds value, a settings combination that fails validation, a duplicate `preset`/`rules` parameter, or an unknown `preset` rejects the WHOLE `rules` parameter (no partial application, no console output): the battle boots with the defaults and the reason is shown in the panel and in `getRulesLinkStatus()`. `?mode=world` ignores custom settings (world mode always plays the defaults; the panel is locked; since section 16 a wolf fight started from the map plays the default battle setup). "Copy link" builds the link for the ACTIVE settings.

**Tutorial, dev scenarios, world mode.** Starting the guided tutorial with custom active settings switches the ACTIVE settings to the defaults and restarts the battle under them (with default settings active nothing restarts, as before); if a turn is running the tutorial is not started. Apply is disabled during the tutorial. When it ends the active settings STAY the defaults; the pending (custom) values stay in the panel, marked "not applied (the tutorial reset the active settings)". `runDevTestScenario` runs under the default settings and restores the previous active settings and rules afterwards (the scenario itself still exits the scenario battle, as before). `startArena` / the legacy reset always use the defaults (since section 16: the default battle setup for wolf fights, current + plain defaults for stag fights).

**Weighted drawing.** `randomAction` picks among actions under the duplicate cap AND with weight > 0, proportionally to the integer weights, consuming exactly one `handRandom()` value: `floor(r * totalWeight)` walked through the cumulative weights. Equal weights give the same index as the old `floor(r * eligible.length)`, so equal-weight hands are unchanged. (Exact for weight 1, where the arithmetic is identical. For other equal weights such as 2/2/2 the identity is verified empirically by r20 on specific seeds, not proven: `floor(r*n*w)/w` could in theory differ by one ulp at an integer boundary.) The enemy intent tags are sliced by the enemy budget and the player tags by the player budget; the enemy branch of `isUnitActionQueueFull` still follows the player budget under `current` (commander: the enemy budget). If no action is eligible (impossible under valid settings; reachable only via dev tools such as "fill Move") it falls back to one value among the actions with weight > 0 (or all actions), ignoring the cap. The hand, carry-over, reshuffle, prepend order and first-match removal are unchanged.

**Layout notes.** `--hand-slots` / `--queue-slots` on `<html>` follow the active hand size / player budget whenever a battle loads. The constant tables (`SETTINGS_BOUNDS`, `SETTINGS_LINK_KEYS`, `RULESET_PRESETS`) are `window` properties and the mutable settings state hangs off `getRulesState()` because r19 pins the top-level declaration inventory of `script.js`. The enemy branch of `isUnitActionQueueFull` still follows the player budget (the planners use `enemyActionBudget` directly). Fixtures: r20 to r24; the P2a fixtures draw at most 500 seeded hands in total (golden-recorded counts).

## 8. Commander preset (experimental: enemy-action and target-selection rules)

A LIMITED EXPERIMENT. Its only differences from `current` are the enemy-action rules below and the target selection of section 9; budgets, hand and draw settings apply to both presets. Presets are the only switch: the rule switches (`COMMANDER_RULES.enemyRules`) are fixed by the preset, not editable. Under `current` nothing changes (all P1/P2a fixtures pass unchanged; the default hash stays `0d3ce2ec6fa6de`).

- **Plumbing.** Panel option "Commander ruleset (experimental: enemy-action and target-selection rules)" (section 9 adds the target selection). The preset lives in `getRulesPresetState()` (`active` / `pending`, beside the settings store so the settings record keeps its shape); it is applied together with the settings on Apply (and rolled back with them if the restart fails), and Restart / R / Play Again keep the ACTIVE preset. Link: `preset=commander` alone or with `rules=`; Copy link emits it; `preset=bogus` is still rejected. Tutorial, world mode and dev scenarios force `current` + default settings exactly as P2a does (the tutorial also resets the preset; dev scenarios restore it). Scenario label: `... · commander (experimental)`. `activeRules` gets `preset: "commander"` only under commander, version `0.4.0-commander-enemy-actions-targets-fallback` (section 9.2; `0.3.0-commander-enemy-actions-targets` after section 9, `0.2.0-commander-enemy-actions` before), and a hash over the effective rules plus the preset, its version (`commanderVersion`, so a version bump changes the hash) and its rule switches (`computeRulesHash(getEffectiveRulesRecord().values) === hash` for both presets).
- **Frozen plan.** The enemy plan is computed once per planning phase (battle load / restart / any reset, and the end of each turn) and frozen: queue edits, reshuffles, preview refreshes and Play only re-render it; the turn start uses it. Flag: `getEnemyPlanState().frozen` (off the top level), set by the pack planner under commander and cleared by `clearEnemyPackActionQueue()` (every reset) and at the turn end. It is BattleState under commander (`enemyPack.planFrozen`, swapped by `withBattleState`, loaded by `loadBattleState`), so `dryRunTurn` equals the real turn.
- **Forfeit, no refund.** A dead enemy's remaining planned actions are forfeited (`forfeited` event: unit, tick, actions); survivors keep their queues; no mid-turn replan (`current` keeps its fresh-pool replan, which can spend more than the budget).
- **Budget ceiling.** Enemy actions spent in a turn never exceed `enemyActionBudget` (asserted in the core); the next turn's plan is fresh from the configured budget and pool. The enemy branch of `isUnitActionQueueFull` uses the enemy budget.
- **Accounting** (events `enemyBudget` + `unassigned` at turn start, `forfeited` at a death, `enemyAccounting` at turn end; an "Enemy actions" block appended to the battle note; all commander-only, wolves mode only: stag mode has no pack plan and no accounting). Assigned = spent + forfeited + unplayed; budget = assigned + unassigned (both asserted). Unassigned reasons: `budget-zero`, `pool-limit` ("the pool has only P actions"), `no-valid-assignment` ("the planner could place no valid use for N pool action(s): ..."). Unplayed = still queued because the battle ended first.
- **Fixtures** r28 (freeze, out-of-band control, dry run = play, BattleState flag, store audit), r29 (forfeit vs current's replan), r30 (accounting cases and note text), r31 (queue limit by team, tags, preset plumbing). Follow-up ledger: r25 to r31 use 72 hands (limit 100). Deferred: target commitment, richer previews, any commander / event-panel UI, `validateOrders` (done in L1 as `validatePlayerOrders`, section 10).

**Known limits of the commander experiment (not fixed).** (1) If an enemy is killed out of band during planning through a dev setter (`setUnitHealth`), its actions stay in the frozen plan; they are skipped at execution and shown as "unplayed" in the accounting, with the note's "battle ended first" wording, which is inaccurate for that case only. (2) When a core error unwinds a turn, the strict accounting check is skipped so it cannot mask the original error; the turn end then runs as before.

## 9. Commander target selection (experimental, commander preset only)

Under the commander preset (wolves mode; `isTargetSelectionActive()`), each player wolf may hold a target. `current` is unchanged: no field, event, note line, marker or input change (r38 replays two r15 turns with every new input path exercised and gets r15's recorded event hashes); its version and default hash `0d3ce2ec6fa6de` are unchanged. Commander identity: version `0.3.0-commander-enemy-actions-targets`, scope label "experimental: enemy-action and target-selection rules" (option, panel notice / summary, Apply message, link status, the note's "Enemy actions" heading), default hash `1ef03d7c79476f` (was `0224eced47f0bf`); the version is part of what is hashed. The rule switches (`COMMANDER_RULES.enemyRules`) and the scenario label suffix (`commander (experimental)`, no scope claim) are unchanged.

- **State.** `unit.targetId` (enemy id or null) and `unit.targetSource` (`"chosen"` clicked, `"auto"` picked by the game) on the unit records; BattleState under commander only (snapshot keys `target` / `targetSource` on PLAYER records; validated: known enemy id with a valid source, or null / null; refused on enemy records and in non-commander states). `withBattleState`, `dryRunTurn` and `loadBattleState` carry them. `resetDevTest` deletes them (restart, scenario load, Play Again, dev reset). No new top-level declaration.
- **Choosing.** During planning, a click on a living enemy (its tile through `handleTileIntent`, or its sprite through the arena click handler) with a wolf selected sets that wolf's target (`chosen`); the click stops propagation so the selection stays. Refused with one status line (appended to the scenario label, shown at `--scenario-label-target-status-opacity` instead of the label's 0.55 until the next label reset): no wolf selected, a defeated enemy, a turn executing. Concealed enemies are targetable.
- **Auto-pick.** When a wolf's queue goes from empty to non-empty (`queueUnitAction`) and it has no LIVING target: the nearest living enemy by grid distance, ties to the lowest id (E1, E2, E3), source `auto`. Never re-picked by later queue edits. At Play, a wolf with a queued Move / Attack and no living target is auto-picked too (covers queues filled directly). A dead target stays recorded until the next first-queue auto-pick or a click.
- **Turn core.** Play commits the targets (`targetsCommitted` event right after `turnStart`, note line `Targets: P1 -> E2 (chosen), P2 -> E1 (auto), P3 -> -`). Move: the existing approach planner receives the committed target instead of the nearest enemy (`getPlayerMoveTargetUnit`); the move preview uses the same target (or Play's auto-pick). Attack: swings at the committed target and hits it if it is alive and adjacent after the moves; otherwise see section 9.2 (adjacent-enemy fallback; with nobody adjacent the existing `miss` event with `reason: "target-not-adjacent"` and `target`). Before 0.4.0 there was no fallback. Engagement stops and the attack-range cap pair a player's attack-intent move only with its committed target (`canAttackIntentPlansEngage`). A Move whose target died earlier in the turn is consumed without movement (`targetSkipped`, reason `target-defeated`); no retarget; Defend is unaffected. An Attack whose target died is skipped the same way only when no living enemy is adjacent (section 9.2). Note lines: `... Move a -> b toward E2 [...]`, `miss: E2 not adjacent`, `Move skipped: E2 defeated`, `Attack skipped: E2 defeated`.
- **Markers.** `unit.targetMarker`: a lazily created overlay beside the enemy sprite in the unit layer, scaled with `--arena-scale-inverse`, tuned by `--unit-target-marker-*` variables; chips list the targeting wolves (`P1 P3~`; auto = dashed, `~`), the selected wolf's target is ringed. Hidden for dead enemies and under current.
- **Fixtures** r32 to r38 (header "REQUIREMENT — target selection"; own hand ledger in `_targets.cjs`, 38 hands, limit 100).
- **Recordings changed (accepted).** r28 and r29 play commander turns, so their recorded event summaries gain the `targetsCommitted` event (r28: count 22 -> 23, event hash `1add507c415dbb` -> `0879f9a11ff695`: the new event, P2's swing now names its auto target E3 and its miss carries reason + target; r29: count 36 -> 37). The commander label / version / hash pins changed in r21 (preset line), r29 and r30 (the note's "Enemy actions" heading), r31 (option, version, commander hashes and the 6-char hash in the custom label / panel summary, panel notice); r21 and r31 fixture sources assert the new label / version.
- **Documented behaviour (kept).** A player Attack swings toward its committed target even when the target is not adjacent (it then misses): the wolf turns to face it, as the existing swing facing does for any swing target. After a dev scenario the commander preset is restored on the exited custom board (`custom board (scenario exited)`), where target selection is active like in any commander battle.
- **Known limits.** Stag mode is out of scope (rules inactive). The browser rendering of the markers, the status line and the document-level deselect are not tested by the current harness.

**Known behaviour change under commander, not covered by a fixture (review note).** An enemy attacking a player wolf whose committed target is a DIFFERENT enemy no longer forms a mutual engagement stop with that wolf (`canAttackIntentPlansEngage`); it only gets the attack-range cap against its own target. ### 9.1 Target selection UX (commander only; UX handlers, no rules change, version and hashes unchanged)

### 9.2 Attack fallback (commander only; version 0.4.0, hash changed)

User rule: standing next to a wolf and whiffing because another enemy was targeted is not fun. When a commander wolf's Attack resolves:
- committed target alive and adjacent: hit it (unchanged);
- target not adjacent or defeated, another living enemy adjacent: hit one adjacent enemy chosen by the SAME selection as with no target (the current preset's: `getAttackTargetFromSnapshot` for the swing intent, then live `getAttackTarget` if it moved away: adjacent by the start-of-tick snapshot, the facing tiebreak, else the first). No new randomness. The `hit` event gains `fallbackFromTargetId` (the committed target) only for such hits; the swing event names the actual victim; the battle note reads `hit E1 ... (fallback: E2 not adjacent or defeated)`;
- nobody adjacent: Miss `target-not-adjacent` as before (`no-target` if the target is dead and the swing ran).
- A dead target: Move is still skipped (`target-defeated`), and an Attack is skipped only when no living enemy is adjacent at the start of the tick (checked before the moves of that tick; an enemy that steps adjacent in the same tick is still caught by the live check at the swing). Move keeps following the committed target.
- Preview / dry run and `applyPlayerOrders` / `runHeadlessTurn` use the same core: r45 verifies preview = play and headless = live. Current preset: no change (r45g; the whole current suite is byte-identical).
- Fixtures: r45 (hand-authored boards a to e, one turn each; headless vs live; current control). Recordings changed: r31 (version pin, commander hashes, label and panel hash), r35 (R35a was a Miss with no fallback: now a fallback hit), r36 (P2's Attack on the defeated E1 now falls back to the adjacent E2), r43 (stateHash only: the BattleState carries the rules version; event hashes unchanged), r44 (rules version and hash). Details: CHECKPOINT-ATTACK-FALLBACK.md.
- In-game text: no hint claimed that an Attack only hits the target, so none changed; the player-visible change is the hit / popup replacing a Miss.

## 10. Player orders, observations and the headless turn (L1)

Built on the existing engine: no second engine, no new turn logic. All in `script.js` under "PLAYER ORDERS AND OBSERVATIONS (L1)". Default behaviour and every existing recording are unchanged (the whole suite passes byte-identical); no UI change.

- **Orders** (plain data, event unit ids): `{ unit: "P1".."P3", action: "Move" | "Attack" | "Defend" }` queues one hand card (first match) for that wolf; `{ unit, target: "E1".."E3" | null }` chooses / clears a commander target. A target order sets the target explicitly (source `chosen`); the UI's toggle (clicking the current target clears it) corresponds to `{ target: null }`.
- **One validation: `validatePlayerOrders(orders)`** -> `{ ok: true, queuedTotal }` or `{ ok: false, index, reason, message }`. Pure (reads only; no queue entries created). Orders are checked in sequence, each against what the previous ones leave, exactly like successive clicks. Reasons in check order: `malformed-orders` (-1), `turn-executing` (-1), `malformed-order`; target orders: `target-selection-inactive`, `invalid-target`, `target-defeated` (target first: the UI's status-line precedence); `unknown-unit`, `unit-defeated`; action orders: `action-budget` (the pack's shared `playerActionBudget`; it is also each wolf's ceiling, there is no separate per-wolf budget), `unknown-action`, `max-same-action`, `card-not-in-hand`.
- **Shared with the UI.** `applyPlayerAction` (card click for the selected wolf) and `handleEnemyTargetIntent` (enemy click) validate their one order through `validatePlayerOrders` and map the reason to their existing refusal (silent / the same status lines). A hand miss in the card path falls through to `consumeAvailableAction`, which adopts a pending direct DOM edit of the hand (shim) and checks again, exactly as before. Card consumption (`consumeAvailableAction`, first match), queueing (`queueUnitAction`, with its first-queue auto-pick and enemy-preview replan) and targets (`setUnitTarget`) are the SAME functions on both paths; inside `runInTurnCore` they change data only and skip their presentation.
- **`maxSameAction`.** It is a DRAW cap: the hand never holds more than the cap of one action and cards only move between hand and queues, so hand + queued never exceed it and the hand check enforces it. The UI never had a separate queue cap; none is added (it would change the dev-tools "Fill Move" path). `max-same-action` names the case "card not in the hand and the pack already queued the cap of it".
- **Headless door: `applyPlayerOrders(orders, { turn })`.** Refuses (returns, never throws, nothing changes) while the battle is not open for orders (`getRulesLockReason`: busy flags, tutorial, no scenario battle) or is over (`battle-over`); adopts a pending direct DOM hand edit (as the UI's next hand edit would) and validates the WHOLE list against that hand; on any refusal the hand data and view items are restored exactly (the edit stays pending); with `turn`, refuses `no-player-orders` when no player action would be queued; only then applies through the shared functions inside `runInTurnCore` (so any presentation call would throw). Atomic by validate-first: a refused list changes nothing. Cards queued earlier by the UI are already out of the hand and orders only take cards still in it, so nothing is charged twice in either direction (r42 / r43).
- **Headless turn: `runHeadlessTurn(orders, { includeEvents })`** = `applyPlayerOrders(orders, { turn: true })` + `drainTurnCore()` -> `{ ok, outcome, observation }` by default. No timers, no randomness added, no LLM. `includeEvents: true` (dev / fixtures only) adds `events`, the full turn log; it includes the next turn's enemy plan, so it is NOT bot-safe and is off by default. The engine's `getTurnEventLog()` dev hook still holds the last turn's log.
- **Observation: `observeBattle()`** (schema `player-observation/1`): a fresh plain-data copy of what a human sees: `config` (grid size, enemy mode), `rules` (preset, version, hash, player / enemy action budget, hand size, max same action), `terrain` (pond, hill, tree, hill levels), `units` (active units only: id, team, type, row, col, direction, health, max health, defeated, concealed; player wolves also movement mode, queued orders and, under commander target selection, target + source), `hand` (cards, reshuffle charges), `outcome`. Excluded: every enemy plan / intent (also the intent tags a human sees for unconcealed enemies; deferred), pack focus and objectives, flee flags, commander plan / accounting state, RNG state and seed, draw weights, enemy pool, debug data. Concealment hides intentions, not locations (as in the game): concealed enemies keep their position, with `concealed: true`.
- **Fixtures** r41 (every refusal reason; atomic refusals with the live fingerprint unchanged, also with a pending direct DOM hand edit; the UI paths validate through the same function with the same reasons), r42 (current: headless = live over two turns, UI-then-headless and headless-then-UI without double charge, unqueue after the door, a lethal board), r43 (commander: the same with target orders, incl. a clear and Play's auto-pick), r44 (observation key walk; RNG: no key name containing seed / rng / state / random and no value equal to the hand-stream state, hand seed or battle seed as a number or string; plain data; copies; the default headless result has no `events` key; rejection does not leak; the door runs no presentation). r42 / r43 opt in to `includeEvents`. Header "REQUIREMENT — L1 player orders"; own hand ledger in `_orders.cjs` (39 hands, limit 60).
- **Presentation after the door.** Like `drainTurnCore`, the door and the headless turn render nothing: hand view, queue rows, intent tags, markers and sprites keep showing the old state until something re-renders them (a UI hand edit rebuilds a stale hand view from the data, r42c). Use in a live browser is dev-only.
- **Known limits.** (1) No turn counter: the engine has none and adding one would be new BattleState (snapshot and r19 recordings would change), so the caller counts turns. (2) Movement mode and removing a queued card have no order type yet (the UI paths for them are unchanged); reshuffle has one since L3a (section 10.1). (3) A core error inside `runHeadlessTurn` behaves as `drainTurnCore` does (no turn-end `finally`, unlike Play; section 3). (4) The door is refused in the guided tutorial and whenever no scenario battle is active (`activeScenario` null, the same rule as Apply), e.g. the world map. (5) A fault inside the apply step (an engine bug, not an invalid order) is not rolled back; validation runs first, so invalid orders never reach it.

### 10.1 Reshuffle order (L3a)

The player's EXISTING reshuffle, now also an order. No rules value, preset default or recording changed (the whole suite r1 to r45 and the Lab fixtures pass byte-identical); no player-visible change.

- **Order** `{ reshuffle: true }`: pack-wide, exactly that key (a `unit`, `action` or `target` key, or any value other than `true`, is `malformed-order`, message "a reshuffle order is exactly { reshuffle: true }"). Handled in sequence with the other orders, like successive clicks: cards queued earlier in the list (or earlier by the UI) are discarded with the hand, NOT returned (the button's behaviour); targets are kept; a target order after it is allowed.
- **Reasons** (validatePlayerOrders): `turn-executing` (list level, as before), `no-reshuffle-charges` ("no reshuffle charges left"; charges are counted in sequence, so `[R, R, R]` with two charges fails at index 2), and for a card order AFTER a reshuffle in the same list `hand-not-observed` ("a reshuffle earlier in this list draws a hand that has not been observed: queue cards in a later call"). The last one is deliberate: the new hand comes from the hand stream, so any hand-dependent verdict on it would let a caller probe undrawn cards for free. It is refused whatever the new hand holds (same reason and message for Move / Attack / Defend), and validation never draws. So a bot reshuffles in one call, observes, then orders. The door adds its usual list-level refusals (busy / `tutorial-active` / `no-scenario-battle` / `battle-over`), and `runHeadlessTurn` refuses `no-player-orders` when the reshuffle left no card queued (e.g. `[P1 Attack, R]`).
- **One implementation.** `reshufflePlayerHandData()` (rules half, core-safe): spend one charge, clear every player queue, empty the hand data, `drawPlayerHandToSize()` (same hand stream, algorithm and order as every draw). The button's `reshuffleActions` now validates through `validatePlayerOrders([{ reshuffle: true }])` (refusal stays silent), empties the view (`clearPlayerHand`), runs that rules half and renders exactly as before (`refillAvailableActions` adopts nothing and draws nothing, then renders the drawn cards with their slide-in; queue rows, controls, enemy preview, button). The door applies `reshufflePlayerHandData()` + `updateEnemyIntentPreview()` (the button's enemy-preview refresh; under commander the frozen plan is untouched) inside `runInTurnCore`. The button's ENABLED state still comes from `canReshuffle()` (charges > 0 and no turn executing: the validator's two conditions); it does not call the validator, so rendering the button records no validation (r41's spies are unchanged). In the guided tutorial the button stays usable (unchanged); the door refuses there, as for every order.
- **Atomicity.** Validate-first: a refused list writes nothing and draws nothing, so the hand-stream position is unchanged (r46 checks the full live fingerprint, which includes the stream state, and the draw counter).
- **Observation.** No new key. `observeBattle()` already shows what the player sees for this decision: `hand.cards` (the current hand; after a turn, the turn-end draw is prepended and unplayed cards are the suffix, which is the only carry-over the UI shows), `hand.reshuffleChargesRemaining`, and each wolf's `queue` (cards a reshuffle would discard). The per-battle total (`reshuffleCharges` in the rules panel) is not in the observation's rules summary; adding it would change r44's pinned keys and golden, so it was left out (follow-up if wanted). No RNG state, seed or deck order.
- **Presentation after the door.** As in section 10: nothing re-renders; the hand view, queue rows and the button's charge count show the old state until the UI re-renders.
- **Fixture** r46 (header "REQUIREMENT — L3a reshuffle order"; L1 hand ledger in `_orders.cjs`: 18 hands, total 58 of 60): headless = live (real button listener) under current and commander, incl. carry-over and the hand-stream state after the reshuffle and after the turn; no charges (rc:0) refused by the validator, door, headless turn and the button (same function, same reason, nothing changed); atomic mixed lists; observation key walk after a headless reshuffle.

## 11. Turn-event hash and visual replay (L3)

### 11.1 `hashTurnEvents`

`window.devTest.hashTurnEvents(events) -> string` (global function `hashTurnEvents`). One synchronous, deterministic hash of ONE turn's event list, shared by the Battle Lab driver (it records each turn's `eventHash`) and the visual replay page (it compares them):
- input: the turn's events as an array (e.g. `runHeadlessTurn(orders, { includeEvents: true }).events`, `drainTurnCore()`, or `getTurnEventLog()` after a played turn); anything else throws `TypeError`;
- normalised by a JSON round trip (so the live log, a drained copy and events parsed from JSON hash alike: `undefined` members drop out exactly as in `JSON.stringify`), written in canonical form (`canonicalizeRules`: object keys sorted, array order kept), hashed with cyrb53 (`hashString53`);
- output: 14 lowercase hex digits (53 bits). Not a security hash.
- It is NOT `dryRunTurn().eventHash` (that one hashes `JSON.stringify(events)` in emission order and is pinned by existing fixtures; unchanged).

### 11.2 Visual replay page (`?replay=1#r=<payload>`)

Watch a recorded Battle Lab battle with the game's own turn flow and animations. Code: script.js "VISUAL REPLAY (L3)"; panel `#replay-panel` in index.html; styles at the end of styles.css. PoC / dev-facing: a viewer for recorded data, not a security boundary.

- **Activation.** Only `?replay=1` (exactly that one query parameter) plus a `#r=` fragment. `resolveBootRoute` returns `{ scenario: null, replay: true }`; the normal boot branch builds a placeholder arena (hidden), then `startReplayMode()` runs. Without `?replay=1` nothing of this runs: no state (`getReplayState.store` stays unset), no class, no listener (r47e). `?replay=0` (or any other value) is a normal boot.
- **Payload v1** (`#r=` = base64url, padding optional, of UTF-8 JSON; contract in tools/lab/CONTRACT.md): `{ v: 1, buildId, scenarioId, seed, preset, rulesQuery, rulesVersion, rulesHash, strategy, botSeed, result, turns: [ { turn, steps, eventHash } ] }`. Exactly these keys (unknown keys refused). `rulesQuery` is `""` or ONE link parameter `"rules=<key>:<value>,..."` (no `&`, `?`, `#`); the preset comes from `preset`. `seed` 0..4294967295; `buildId` 64 hex; `rulesHash` / `eventHash` 14 hex; `result` one of win / loss / draw / timeout / error; `turns` 1..60 numbered 1, 2, ...; `steps` 1..2 lists of at most 64 orders; every step but the last must be exactly `[{ "reshuffle": true }]` (bot protocol v2); orders are `{ unit: P1..P3, action: Move|Attack|Defend }`, `{ unit, target: E1..E3|null }` or `{ reshuffle: true }`, exact keys (their legality is the game's decision at replay time). Encoded payload at most 262144 characters.
- **Refusals** (nothing starts, the board is hidden, the panel shows `Replay refused: <reason>`): `payload field "<path>" is missing / is not a v1 replay payload field / must be ...` with paths like `turns[1].steps[0][2]`; `?replay` (extra or duplicate query parameters); `#r` (missing, empty, too long, not base64url UTF-8, not JSON). r48d pins every message.
- **Build identity.** The page fetches `./build-id.json` (`{ "buildId": "<64 hex>" }`, written by `pnpm build`, section 11.3). Different from `payload.buildId` -> refused, showing both 12-char short IDs. Unavailable (no fetch, HTTP error, network error, not JSON / no buildId; the vite dev server answers `/build-id.json` with its HTML page, so there it is "not JSON") -> visible warning `build identity unavailable; relying on rules hash and per-turn event hashes (<reason>)` and the replay continues.
- **Setup only from the payload.** `preset` + `rulesQuery` go through the strict link parser (`parseRulesParams`; a rejection is a refusal naming the reason) and are applied by the normal boot path (`resolveBootRules(route, search)`, which gained the optional `search` argument; the boot call is unchanged), then `loadScenario(scenarioId, seed)` (an unknown scenario is refused, never the intro fallback). Then `activeRules.version` / `.hash` must equal `rulesVersion` / `rulesHash`; otherwise refused naming exactly the differing field(s) with both values. Current settings are never substituted.
- **Playback.** Per turn: every step but the last through `applyPlayerOrders(step)`, the last through `applyPlayerOrders(step, { turn: true })`; after each step `presentReplayStep` renders what the headless door does not (hand view, with the Reshuffle button's slide-in after a reshuffle; queue rows; controls; enemy intent tags; target markers; presentation only) and waits 600 ms; then `executePlayerActionQueue()` (the Play button's driver: the existing animations, the same code path). Then `hashTurnEvents(lastTurnEventLog)` is compared with the turn's `eventHash`. A mismatch stops playback: `Divergence at turn N: recorded <h1> vs replayed <h2>`, the board stays visible. A refused order list stops playback with the game's reason (`Playback stopped at turn N, step S: the game refused the recorded orders (<reason>: <message>).`). Play / Pause (autoplay, 900 ms between turns; Pause takes effect when the turn on screen ends), Next turn (one turn), Restart replay (the same setup again from the payload: rules, scenario, seed, so terrain, units, queues, hand and hand stream reset; r47c). The panel shows the turn `k / N`, the recorded orders of that turn as text (e.g. `Step 1: reshuffle`, `Step 2: P1: Move, Attack -> target E2; P2: Defend`) and, at the end, the recorded result next to the replayed outcome. No bot runs and nothing is generated: only recorded steps are applied.
- **Input lock.** While replay mode is on, `isReplayInputLocked()` is true except during the replay's own synchronous call into `executePlayerActionQueue`. Guards: Play (`executePlayerActionQueue`), card clicks (`applyPlayerAction`), Reshuffle (`reshuffleActions`), target clicks (`handleEnemyTargetIntent`, `handleTileIntent`), the arena click / key handlers, the queue rows and `removeUnitActionAt`, Restart / R (`restartBattle`), Play Again (`resetGame`), rules Apply (`applyPendingSettings` refuses `replay-active`) and the tutorial settings switch. A capture-phase `click` / `keydown` blocker on `window` stops everything outside `#replay-panel` (it only stops propagation, so browser shortcuts still work); CSS hides the dev tools, Restart, Tutorial and Play Again buttons. The dev door (`window.devTest.*`) is not player input and is not locked.
- **Top level.** No new top-level declaration (r19's inventory unchanged): state in `getReplayState()`, limits in `getReplayLimits()`.
- **Fixtures** r47 (hashTurnEvents properties; replay = headless recording for all 3 turns: per-turn hashes, final BattleState incl. hand stream, last turn's events, observation, battle note; Restart identical; input lock with a normal-boot control; normal boot unchanged) and r48 (tampered hash -> divergence at turn 2; build mismatch; rules mismatches and link / preset / scenario refusals; 41 malformed links / payloads; on-page errors; four "unavailable" warnings). One hand-authored 3-turn battle (intro, seed 1, commander, `rules=rc:3`; turn 1 = reshuffle step then card step), its hashes recorded once headlessly per run; payload variants are hand-written edits. Own hand ledger in `_replay.cjs` (58 of 60). Harness seam: `_replay.cjs` wraps `vm.createContext` for one `loadGame` call to add `location.hash` and a fetch stub; tests/harness is unchanged.
- **Known limits.** Not covered by the harness: real browser rendering of the panel, the capture-phase blocker on real events (r47d calls it with stub events), CSS hiding, timing feel. Pause cannot cut a turn mid-animation. A payload whose battle ends before its last recorded turn stops with the door's `battle-over` refusal. The placeholder arena built behind a refused page is the procedural (world-route) arena, hidden by CSS.

## 12. Battle Lab search (search-benchmark; Lab-side, no gameplay change)

`tools/lab/search.cjs` (BOTS.md "search-benchmark") evaluates candidate orders through `game.ev` on existing global functions, without any `script.js` change: `snapshotBattleState` + `withBattleState` (the copy), inside it the door's per-order functions (`setUnitTarget`, `consumeAvailableAction`, `queueUnitAction` in `runInTurnCore`) and `guardTurnCore(runTurnCore(createTurnContext(...)))` drained up to the turn-end `recovery` step; `validatePlayerOrders` first. So these internal functions now have a Lab caller too; the separation schedule (section 1) must keep them reachable in the dev context. The per-order loop is a Lab-side copy of `applyPlayerOrders`' apply step (the door itself refuses during a swap); tests/lab/s2 and s4 check prediction = real turn on hand-placed boards.

**RNG finding.** The only gameplay RNG is the hand stream (`handRandom`, used by `randomAction`: the turn-end refill and a reshuffle); turn resolution is deterministic given the state, the orders and the enemy plan (frozen under commander). A copy carries the stream position, so a FULL copied turn would compute the real next hand; the search therefore stops before the hand draw (and gives the copy a fixed neutral stream), never reads the next enemy plan, and never evaluates a reshuffle. What an evaluation does reveal is the exact combat outcome of the turn under the hidden enemy plan (full-information, allowed for this benchmark only). Under `commanderdraw` the enemy draw stream is a second gameplay RNG; it is handled the same way (section 13).

## 13. Commanderdraw preset (experimental: random enemy action draw)

A LIMITED EXPERIMENT, opt-in only: preset `commanderdraw` = every commander rule (sections 8, 9, 9.2) plus ONE change: the enemy's action list is DRAWN at random each planning phase instead of being the fixed pool expansion. `current` and `commander` are byte-identical (whole suite; hashes `0d3ce2ec6fa6de` / `1ee7c8d5a26ec1` unchanged).

- **Switch.** A new preset, not a settings key: a settings key would change the settings record (and every hash); a commander-only switch would change commander's hash. `isCommanderRules()` is true for both commander presets, `isEnemyDrawRules()` only for `commanderdraw`. The name has lowercase letters only because the replay payload, the Lab driver and the manifest accept only such preset names (`commander-draw` would fail all three). Link: `?scenario=intro&seed=1&preset=commanderdraw[&rules=...]`; panel option "Commander draw ruleset (...)"; label `· commander draw (experimental)`; observation `rules.preset: "commanderdraw"`. Tutorial / dev scenarios force `current` as for commander (world mode too until section 16).
- **Identity.** `window.COMMANDER_DRAW_RULES`: version `0.1.0-commanderdraw-enemy-random-draw`; hashed record = the commander record under preset `commanderdraw` plus `enemyDraw` (version, weights, cap, seed mix). Default numbers: hash `197edd95522f77`; equal budgets `rules=pab:4,hs:4,rc:2,cap:3,eab:4` `149db90d99fe1b`, `...5...` `197edd95522f77` (= defaults), `...6...` `0c62352e2b5ed9` (r49).
- **Draw.** Exactly once per planning moment (`planEnemyPackTurnRules`: battle load / restart / any reset that replans, and each turn end), `drawEnemyPlanPool()` draws `enemyActionBudget` actions: weights Move / Attack / Defend 1 / 1 / 1 by default (per battle through the link since 13.1; not settings keys), same-action cap 3 per list, raised to `ceil(budget / 3)` when the budget exceeds 9 (only budget 10: cap 4). - **Stream.** Separate from the hand stream: seeded at every scenario load from the battle seed, `x = (seed ^ 0x9e3779b9) >>> 0; imul(x ^ (x >>> 16), 0x85ebca6b) >>> 0` (a bijection on 0..2^32-1), same `createSeededRandom` (mulberry32). - **Frozen, no redraw, no refund.** The plan stays frozen during execution (commander). A dead enemy's actions are forfeited (no casualty redraw); drawn actions the planner cannot place are `unassigned` (`no-valid-assignment`), not refunded or carried over; the enemy has no reshuffle. The accounting's `pool` is the drawn list; the note reads `Enemy actions (commanderdraw, ...)` / `Budget 5 | drawn 5: ...`.
- **BattleState** (commanderdraw only; validated, refused under other presets): `rng.enemyDrawState` (stream position) and `enemyPack.drawnPool` (list or null), in `getEnemyDrawState()` (off the top level; r19 unchanged), swapped by `withBattleState`, written by `loadBattleState`. So `dryRunTurn` equals the real turn and a copy's draw never moves the live stream (r50a, r49e).
- **Search benchmark.** `search.cjs` stops at the turn-end `recovery` step, before the next plan's draw, and gives the copy a neutral enemy position (`NEUTRAL_ENEMY_DRAW_STATE`) like the hand stream; it keeps the current frozen plan's `drawnPool`. If a plan were NOT frozen at decision time (only after a dev reset), the copy would plan from the neutral stream: no leak, but a wrong prediction. s6.
- **Fixtures** r49 (identity, pinned lists for seeds 1..3, structure for budgets 0..10, live plans over 3 turns, stream isolation, BattleState), r50 (frozen plan, dry run = Play, unassigned, budgets 0 / 10, forfeit), r51 (visual replay of a 4v4 3-turn recording), Lab s6 and g7.
